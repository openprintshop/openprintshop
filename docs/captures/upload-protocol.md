# Заливка gcode на Centauri Carbon 2 (разведано 20.07.2026)

Единственное, чего бот раньше не умел: файл приходилось класть на принтер слайсером вручную.
Протокол восстановлен статическим анализом веб-интерфейса ElegooSlicer
(`C:\Program Files\ElegooSlicer\resources\plugins\elegoolink\web\lan_service_web\index.html`)
и проверен живой заливкой (6.16 МБ за ~1 с).

## Протокол

Не multipart и не POST — **последовательные `PUT`** одного и того же пути, чанк за чанком,
смещение задаётся заголовком `Content-Range`.

```
PUT http://{ip}/upload            (локальная память; /upload/udisk, /upload/sdcard — прочие)
Content-Type:  application/octet-stream
Content-Range: bytes {off}-{end-1}/{total}
X-Token:       {ELEGOO_ACCESS_CODE}
X-File-Name:   {urlencode(имя.gcode)}
X-File-MD5:    {md5 ВСЕГО файла, lowercase hex}
<тело: кусок файла, 1 МиБ>
```

Ответ на каждый чанк — JSON: `{"error_code": 0, "offset": <курсор сервера>}`.
Отдельного «commit» нет: последний чанк завершает заливку, принтер сам сверяет MD5.
После этого файл появляется в списке метода 1044 (`storage_media: "local"`), уже с разобранными
метаданными (слои, граммы, цвет/материал) — прошивка парсит gcode сама.

## Главная ловушка: одно соединение на всю заливку

**Все чанки обязаны идти по ОДНОМУ keep-alive соединению.** Если открывать новое TCP на каждый
чанк (как делает `urllib.request`), прошивка (`libhv/1.3.4`) начиная с 4-го чанка отвечает
**HTTP 429 Too Many Requests**, и паузами это не лечится (проверял до 1.5 с между чанками —
429 приходит ровно на 4-м). Браузер шлёт `fetch` по одному соединению, поэтому в веб-интерфейсе
проблемы нет.

Реализация: `http.client.HTTPConnection` на всю заливку (`elegoo.upload_gcode`). С ним 6 МБ
уходят за ~1 с без единого отказа. Если 429 всё же прилетел — соединение переоткрывается с
паузой (`UPLOAD_THROTTLE_WAIT`).

Симптом неправильной реализации: часть чанков проходит, а в конце `error_code 9004`
(`MD5CheckFailed`) — потому что повторы после 429 дописывают дубли и файл на принтере
получается длиннее оригинала.

## Прочее

- Принимается **только `.gcode`** (веб-интерфейс проверяет тем же условием); `.3mf` не заливается.
- Чанки строго последовательно — сервер ведёт свой курсор (`error_code 9000` = FileOffsetMismatch),
  параллелить нельзя.
- Одноимённый файл принтер удаляет сам перед записью (`9010` — если не смог).
- Коды ошибок: 1000 неверный X-Token, 9000 рассинхрон смещения, 9001/9002/9003 ошибки записи,
  9004 не сошёлся MD5, 9007 путь не существует, 9010 не удалить одноимённый, 9999 прочее.
- Лимита размера в клиенте нет; у нас стоит предохранитель 200 МБ на эндпоинте.
- `storage_media` в MQTT пишется через дефис (`local` / `u-disk` / `sd-card`), а в HTTP-путях —
  слитно (`/upload`, `/upload/udisk`, `/upload/sdcard`). Два разных словаря, легко перепутать.

## Соседние MQTT-методы (из того же анализа)

- **1047 DeleteFile** — `{"storage_media":"local","file_path":["имя.gcode"]}`. `file_path` это
  **массив**, даже для одного файла: строка → `error_code 1003` (InvalidParameter). Имя берётся
  ровно как в списке 1044 (без каталога и ведущего слеша). Пакетное удаление — тем же массивом.
  Не путать с историей: у 1038 HistoryDelete поле называется `list`.
- **2001 LoadFilamenting** — `{"canvas_id":0,"tray_id":слот−1}`, формат идентичен 2002
  (выгрузка). Доп. полей нет; тип/цвет/температуры филамента задаются отдельно методом 2003
  SetFilamentInfo. Занятый принтер вернёт 1009 PrinterBusy.
- Коды ответов прошивки: 1000 TokenValidationFailed, 1001 UnknownInterface, 1002
  FolderOpenFailed, **1003 InvalidParameter**, 1004 FileWriteFailed, 1005 UpdateTokenFailed,
  1007 FileDeleteFailed, 1008 ResponseDataEmpty, 1009 PrinterBusy.
